# Threats to validity

The report must address each threat below (spec §13). This file is owned by both IC and SG. The first section repeats the spec's list, each with where the project handles it. The second adds threats found while building and testing the adapters, with the evidence for each. Entries marked **open** still need data or a decision before the report.

## From spec §13

- **Implementation, not scheme.** Ratios across codebases mix scheme cost with engineering quality. Handled by the within-codebase pairs (S1 and S2 against S0-cpp, M1 against M0) and the S0-go against S0-cpp ablation. **Open:** the ablation needs grid data.
- **Different security levels and parameters.** Every record carries `scheme_params`. The report claims equal security only where the papers state it.
- **Fake versus real preprocessing.** Spec rule 2. Every adapter calls the real setup and preprocessing (`src/adapters/*/README.md`).
- **S2 lacks the digest check.** Upstream has no `DigVer`, and rule 1 forbids writing it (decision 5). S2's overhead against S0-cpp understates the paper's full scheme.
- **VeriSimplePIR ratios against a different baseline and at different sizes.** We compare with the paper's 64-bit SimplePIR bars (decision 6) and reproduce its communication ratios at its sizes analytically (decision 7).
- **LWE+ `tECC` values partly derived.** The 16 MiB and 128 MiB values come from the authors' `scripts/integrity_amplification.py` at the 2^-64 target, not from the paper (decision 9).
- **Single-threaded, single machine.** The main grid runs single-threaded, two-server timing is in-process, and network effects are modelled.
- **Trust assumptions differ.** Two-server schemes assume non-colluding servers. A cost comparison is not a security equivalence.
- **Apple silicon versus the papers' x86-64 hardware.** Compare ratios, not absolute times.
- **Performance and efficiency cores, no pinning.** A single-threaded run may move between core types. RQ7 stops at W = 6.
- **Unified memory bandwidth.** No bandwidth counters (§6). Multicore results depend on this machine's memory system.
- **Portable cryptoTools backends in VeriSimplePIR.** arm64 builds use the portable `block` and AES, not the authors' SSE2 path.
- **Go 1.27 instead of 1.19, and clang instead of GCC.** Both arms of each pair use the same toolchain.
- **Thermal throttling.** **Open:** the analysis checks each cell for drift across repetitions.
- **Load generator and server on one machine (RQ6).** **Open:** gate G7 checks the load generator's CPU on the RQ6 rows. RQ6 and RQ7 run at one cell, 128 MiB × 1 KiB, with 3 load runs per point (decision 25). The decision assumed that S1, S2 and S3 do not fit at 1 GiB. The grid shows that S2's and S3's online phases do not fit, but S1's does, at 11.55 to 11.72 GiB (`notebooks/20_grid_conditions.ipynb` cell 3). So their results say nothing about how the gap under load moves with database or record size.
- **Emulated networks and loopback (RQ3b).** `dnctl` rounds a delay up to the kernel tick, which is 10 ms on this Mac (`sysctl kern.clockrate`). Broadband's and mobile's one-way delays (10 and 30 ms) are whole ticks, but LAN's 0.25 ms is not, so LAN runs at 1 Gbps with no added delay. Its calibration checks bandwidth and records the RTT loopback gives, and F9 models LAN at that measured RTT (decision 22). **Open:** needs the dummynet runs.
- **Serving wrappers are ours.** One protocol and one server loop per language serve every arm (`docs/serve_protocol.md`).
- **Recovery policies are modelling choices.** Honest replicas, a budget of 3 further attempts, and no `retry_same` (decision 12, `configs/recovery_policies.yaml`).
- **RQ4 runs at one cell with reduced counts.** The spec's RQ4 would take an expected 1115.5 h on this Mac (`notebooks/09_rq4_plan.ipynb` cell 1), and its shrink to 1 GiB × 1 KiB leaves S1, S2 and S3 no cell. So RQ4 runs every arm at 128 MiB × 1 KiB, with S3 retrieving one bit and S4 at 64 KiB, which is not a focus cell (`notebooks/10_rq4_day.ipynb` cell 1). The trials keep 100 per case for `abort` and `switch_replica`, but S3 and S4 get 30. There are no `re_preprocess` trials: at fault rate 1 the same server cheats on every attempt, so each would end aborted after three offline phases. Offline faults get 3 repetitions for S1 and S2 and 10 for the S0 arms. The sweep keeps one honest control per arm and only the rates that expect at least 5 cheats, and S3 and S4 get 50 queries per rate. `re_preprocess` runs at f = 0.1 only, with 50 queries. Its recovery cost therefore rests on 8 recoveries per arm, and S1 and S2 drew the same 8 queries, because they share a seed. Its F13 point is checked against the cost computed from the offline Runs. The measured mean is 1.98 times the computed one, but the 95 % interval over 50 queries is wide enough to contain it (`notebooks/11_rq4_analysis.ipynb` cell 5). There are no 1 GiB or 32 B results for RQ4.
- **F13's computed cost assumes what a rejected further attempt costs.** The trials' replicas are honest, so they never measure a rejected further attempt. The model takes it to cost what a rejected first attempt costs. At f = 1, where every attempt is rejected, the sweep points lie within 1.3 % of that assumption (`notebooks/11_rq4_analysis.ipynb` cell 5).
- **Stale code.** The upstream repos are 2023 to 2024 research prototypes.

## Found while building the adapters

- **Measurement conditions on a laptop.** `caffeinate` cannot stop clamshell sleep, and macOS's monotonic clock stops while the machine sleeps. A timing run with the lid closed therefore shows normal timed spans while taking hours. This happened once, and that run was discarded. Every timing run since checks wall against monotonic time, power source and lid at both ends, and fails otherwise (`harness/hygiene.py`, `notebooks/06_s4_cost.ipynb` cell 1). The check caught it again on 12 November, when the lid closed during S3's 1 GiB offline cell. That attempt slept 1625 s and is kept in `results/raw/all-20261112_tier1/rejected/`. The check does not see other processes' load. The Tier 1 grid ran beside the usual background processes, and its medians lie 0.864 to 1.061 times those of earlier runs of the same cells, with a median of 1.014 over 32 cells (`notebooks/20_grid_conditions.ipynb` cell 1). The low end is M1 offline against notebook 07's feasibility run, which started under heavier load.
- **S4 is measured only up to 1 MiB.** At the spec's repetitions an S4 offline cell takes 34 minutes at 1 MiB. So the 16 MiB and 128 MiB costs are extrapolated from a linear fit (exponents 0.98 for the digest and 0.97 per query) and labelled as such (decision 10, spec v1.6, `notebooks/06_s4_cost.ipynb` cells 2 and 3). The analysis refits every metric to the grid's own S4 medians at 64 KiB, 256 KiB and 1 MiB (`analysis/extrapolate.py`), F3 draws the extrapolated points dotted, and target R8 (DDH at 1 GiB) rests on that extrapolation alone. S4 has no RQ4 focus cell for the same reason.
- **Upstream SimplePIR mis-addresses packed entries.** When entries are smaller than a Z_p element, `MakeDB` packs several into one, but `Query(i)` and `Recover(i)` still address element `i`. With real setup on a seeded one-bit database, upstream's own call sequence returned the right bit for 18 of 200 queried entries, a wrong bit for 7, and panicked on 175; 8-bit entries, which do not pack, came back right 200 of 200 times (`notebooks/15_rq1_anchors.ipynb` cell 1). The README's one-bit numbers come from a benchmark that uses random hints and checks no answer. The S0-go adapter's one-bit anchor (decision 21) addresses packed elements itself and checks every bit; costs do not depend on which column is queried.
- **The SimplePIR README's units are read as binary.** Its "121 MB" hint and "242 KB" online traffic match the hint and query formulas only as MiB and KiB. The ±5 % tolerance gives targets R23 and R24 the same verdict either way (`docs/reproduction_targets.md`).
- **An upstream M1 client can be made to allocate up to 96 GiB.** `merkle.DecodeProof` allocates as many slice headers as a corrupted proof's first 4 bytes say, before reading any hash. The apir-code adapter refuses such decodes, which always panic, and records the same rejection with `client_recover_s` null. So faulted M1 repetitions carry no reconstruction time for those answers. The refused decodes would have allocated a median 47.2 GiB (`notebooks/04_p7_memory_findings.ipynb` cell 2). This is a finding about the library, not something the benchmark adds.
- **Fault injection can slow the timed work around it.** S3's `wrong_record` builds the wrong answer from a second client's query, outside the timed spans. Upstream's LWE client keeps its last query's state, about 1.9 GB at 128 MiB. In notebook 10's run, the second client lived for the whole run, and its garbage was collected only at the next repetition. S3's query generation under `wrong_record` took a median 0.95 to 1.33 s per Run, honest queries included, against 0.59 s after the fix, with peaks of 9.67 to 10.71 GiB against 6.66 to 6.86 GiB. Commits `a053272` and `b353acc` give each shadow query a fresh client and collect after every injected fault, untimed. Notebooks 12 and 13 rerun the affected Runs. The same check found that M1's `recovery_s` summed its two servers' answers, while the first attempt counts the slower one. So an M1 recovery attempt read 0.074 s against 0.037 s, and `a053272` counts the servers in parallel (`notebooks/11_rq4_analysis.ipynb` cell 7). RQ4's Runs therefore come from three builds of the apir adapter that differ only in these paths. The other apir Runs keep notebook 10's build: S4, M0, and M1 under `abort`. Their shadow queries are small, and S4's and M1's F13 points lie within 2.9 % of the computed cost (cell 5). They were not rerun to show that the extra collection changes nothing.
- **`drop_server` has no client timeout.** No adapter models how long a client waits before it gives up on a withheld answer, so under `drop_server` the time to a correct answer is a lower bound (`src/adapters/README.md`, "Recovery").
- **Cells that do not fit in this Mac's memory.** A cell gets at most 14 GiB, because macOS and the editor need about 2 of the 16 GiB. S1 and S2 at 1 GiB, S3 at 1 GiB, and M1 at 1 GiB with 32 B records need more, so those cells are `oom` and the 1 GiB comparisons for S1, S2 and S3 are missing (`notebooks/08_memory_ceiling.ipynb` cell 2). M1 at 128 MiB with 32 B records fits at 11.74 GiB, and S0-cpp at 1 GiB at 9.76 GiB (`notebooks/07_grid_feasibility.ipynb` cell 2). Cells that close to the cap run while macOS compresses and swaps other processes' memory, so their times may include paging. Notebook 08 records swap use before and after each cell. In the Tier 1 grid, 19 of 206 (cell, phase) runs did not finish (`notebooks/17_tier1_grid.ipynb` cell 2). S2 at 1 GiB fails in both phases. S1 at 1 GiB fails offline, but its online phase fits at 11.55 to 11.72 GiB. M1 at 1 GiB fails at 32 B and 256 B in both phases. M1 at 128 MiB × 32 B fails offline, but its online phase fits at 11.65 GiB (`notebooks/20_grid_conditions.ipynb` cell 3). Where both phases fit, the offline peak is 1.32 to 1.71 times the online one for the S0, S1 and S2 arms. Part of that comes from how the adapters run repetitions, not from the schemes. VeriSimplePIR preprocesses each offline repetition in a forked child, and at 128 MiB × 32 B that child adds 1.57 GiB against 0.90 GiB when the same preprocessing runs in-process (cell 5).
- **S3 at 1 GiB offline runs in compressed memory and did not finish.** Upstream's LWE database holds one byte per bit, 8 GiB at 1 GiB, and the process peaked at 10.54 GiB (`notebooks/20_grid_conditions.ipynb` cell 6). macOS held most of that compressed while the cell ran, which is the likely cause of the slowdown. Against a linear expectation of 890 s per repetition from the smaller sizes, the three attempts took 1.19 times (repetition 0 before the lid closed), 1.76 to 3.02 times (beside interactive use), and 1.57 to 3.06 times on a quiet machine. Both full attempts hit the 7200 s timeout after three of four repetitions (`notebooks/20_grid_conditions.ipynb` cell 2). The cell is recorded as `timeout`. Its partial rows stay in the raw file, but the analysis leaves out every row of a cell that failed (`analysis/frame.py`, `load_runs`). So RQ1's 1 GiB targets for S3 (R5, R9 to R12) are missing, the online ones because S3's online phase does not fit at 1 GiB (`notebooks/18_rq1_reproduction.ipynb` cell 3).
- **Memory is sampled, not traced.** Peak footprints come from polling every 0.1 s, so a short peak can be missed. On reruns the S3 peak moved between 0.27 and 0.29 GiB (`notebooks/04_p7_memory_findings.ipynb` cell 3). Adapters in the tests run under a 2 GiB cap, and a cell that needs more fails rather than shrinks.
- **VeriSimplePIR leaks memory per online repetition.** Upstream `Matrix` has no destructor, so peak RSS grows by about 44 KiB per S1 online repetition at 1 MiB in the parent process. Offline phases run in a child process so their leak dies with it (`src/adapters/vsp_cpp/README.md`, "Known limits"). Online `process_peak_rss_bytes` therefore grows with the repetition count.
- **VeriSimplePIR pads small databases with long records.** Upstream sizes its matrix from the entry count alone, so a long record at a small database runs on a larger matrix. Every record carries `scheme_params.padding_factor`, and the analysis flags cells above 1.1 (decision 19).
- **Thread safety rests partly on reading the code.** The Go race detector and ThreadSanitizer found no race in any serve-mode arm, and both caught a deliberate one (`notebooks/05_serve_thread_safety.ipynb` cells 2 and 3). Neither sees inside the libraries' C and C++ code, so concurrent `Answer` calls there rest on the code reading in `docs/serve_protocol.md`.
- **Serve and client mode seed what bench mode draws at random.** S0-go uses upstream's `InitCompressedSeeded`, and VeriSimplePIR draws `A` with upstream's own `pseudorandom`, both keyed by `--seed`, so a client can rebuild the server's offline state. The distribution is the same as in bench mode, which keeps upstream's draw (`docs/serve_protocol.md`, "Session").
