# apir_go

Adapter for Colombo et al.'s apir-code (`third_party/apir-code`, module `github.com/si-co/vpir-code`, pinned at `35cabd6`). It serves four arms and follows the contract in `../README.md`.

| Arm | Scheme | Upstream calls |
|---|---|---|
| S3 | single-server LWE with integrity amplification (LWE+) | `database.Digest`, `server.NewAmplify`, `client.NewAmplify` (`Query`, `Answer`, `Reconstruct`) |
| S4 | single-server DDH on P-256 | `database.CreateRandomEllipticWithDigest`, `server.NewDH`, `client.NewDH` (`QueryBytes`, `AnswerBytes`, `ReconstructBytes`) |
| M0 | classic two-server XOR PIR | `database.CreateRandomBytes`, `server.NewPIR` twice, `client.NewPIR` (`Query`, `Answer`, `Reconstruct`) |
| M1 | two-server Merkle authenticated PIR | `database.CreateRandomMerkle`, then the same calls as M0 |

apir-code is GPL-3.0, so this directory is GPL-3.0 too (`LICENSE`, copied from `third_party/apir-code/LICENSE.md`, plan decision 17).

## Build

From the repository root:

```sh
GOTOOLCHAIN=local CGO_ENABLED=1 CC=$(brew --prefix llvm)/bin/clang \
  go -C src/adapters/apir_go build \
  -ldflags "-X main.upstreamSHA=$(git -C third_party/apir-code rev-parse HEAD)" \
  -o ../../../build/adapters/apir-adapter .
```

It needs `patches/apir-code/01-matrix-cgo-flags.patch` applied (`make patch`). `go.mod` replaces the upstream module with the submodule, and every dependency resolves from the module cache that `make setup` fills.

## Data and layout

- The database and the query indices come from ChaCha8 streams keyed by SHA-256 of a label and `--seed` (`measure.go`). The database, the indices, the faults and each client's randomness use separate streams, so a fault never shifts an index. apir-code's Gaussian noise uses its own unseeded global generator.
- `geometryFor` (`arms.go`) is the one place that converts bytes to the library's units. apir-code's constructors take the database length in bits.
- S3 and S4 use the library's square bit matrix (`database.CalculateNumRowsAndColumns`, which rounds up to the next square). `n_records` is `8 × db_bytes`, and the indices are drawn from that range.
- M0 and M1 store blocks of `record_bytes` in a matrix, as the upstream tests do (`pir_test.go`, `merkle_test.go`). The row count is the largest divisor of the block count not above its square root, so no block is dropped. For the grid's powers of two this is `2^floor(k/2)` rows.
- S3 lays out its bit matrix in the adapter with the same loop as `database.CreateRandomBinaryLWE`, then times `database.Digest` alone. That constructor computes the digest inline, so calling it would put database generation inside the timer.
- `correct` compares the client's output with the adapter's generated bytes, not with the library's copy of the database.

## Timed spans

Each timer wraps one scheme call. All four arms run on one OS thread (`runtime.GOMAXPROCS(1)`, plan decision 16). `runtime.GC()` runs untimed before each repetition, as `simulations/simul.go` does.

| Metric | S3 | S4 | M0 | M1 |
|---|---|---|---|---|
| `public_params_s` | null. `A` is expanded from the fixed `utils.SeedMatrixA` inside `Digest` and inside every `Query`, so its cost is in those spans. | null | null | null |
| `server_preproc_s` | `database.Digest` | the whole `CreateRandomEllipticWithDigest`. It computes the row digests inline. Its other work is copying the pre-generated bytes and masking them to bits. | 0, no preprocessing | the whole `CreateRandomMerkle`. It builds the tree and writes each block with its proof. Its other work is copying the pre-generated bytes. |
| `client_offline_s` | `client.NewAmplify` | `client.NewDH`, which checks the row digests against the global digest | `client.NewPIR` | `client.NewPIR` |
| `query_gen_s` | `Amplify.Query` | `DH.QueryBytes` (includes point compression, the only API) | `PIR.Query` | `PIR.Query` |
| `server_answer_s` | `Amplify.Answer` | `DH.AnswerBytes` (includes decoding and encoding, the only API) | `PIR.Answer`, per server | `PIR.Answer`, per server |
| `client_recover_s` | `Amplify.Reconstruct` | `DH.ReconstructBytes` (includes decoding, the only API) | `PIR.Reconstruct` | `PIR.Reconstruct` |

S3, S4 and M1 verify inside reconstruction (`client/lwe.go` returns `REJECT` when a column decodes to neither 0 nor `t`; `client/dh.go` returns `reject` when a row fails its digest check; `client/client.go` `reconstructPIR` returns `REJECT!` when the Merkle proof fails). So `verify_fused=true` and `client_verify_s` is null for them. Any error from reconstruction is `detected=true`. M0 has no verification, so `verify_fused=false` and `detected` is null.

## Encoding

Bytes are `len()` of these messages.

- **S3.** The query and the answer are each `matrix.MatricesToBytes` of the `2·tECC+1` matrices: a 4-byte length, then per matrix an 8-byte rows/cols header and 4 big-endian bytes per element. The offline download is `matrix.MatrixToBytes(digest)` (`offline_down_bytes_hint_only`) plus the 16-byte seed of `A` (`offline_down_bytes`). The client stores both.
- **S4.** apir-code's own byte encoding: concatenated compressed P-256 points (33 bytes each). The offline download and client storage are `SubDigests` plus the global `Digest`.
- **M0, M1.** The library's queries and answers are already byte slices: a share of `cols/8 + 1` bytes per server, and `rows × stored_block_bytes` per answer. M1's stored block is the record, its encoded proof and one pad byte. M1's offline download and client storage are the 32-byte Merkle root. M0 has none.

## Analytical sizes

`analytical` carries upstream's own formulas only.

- S3. `simulations/simul.go` (`pirLWE`) counts `Matrix.BytesSize()` = `rows × cols × 4` per matrix, which leaves out the encoding headers. So `up_bytes` = `(2t+1)·4·L`, `down_bytes` = `(2t+1)·4·M`, and `offline_down_bytes_hint_only` = `4·n·M`. At 1 MiB the headers make the measured size 0.07% larger.
- S4, M0, M1. Upstream gives no formula. `simul.go` (`pirElliptic`) and `simulations/multi` count `len()` of the same bytes, so all three keys are null.

## Faults

Faults change the serialised answer of one server, chosen at random from the fault stream, before the client parses it.

- `flip_answer_bit` flips one bit drawn uniformly from the bits the honest output depends on (contract rule):
  - S3: bit 31 = `log2(q/p)` (q = 2^32, p = 2) of the queried column's element, in one of the `2t+1` sub-answers. Lower bits stay below the decoding bound `B` and decode to the same value.
  - S4: any bit of the answer. The client checks every row against its digest.
  - M0: any bit of the queried row's block.
  - M1: any bit of the queried row's stored block, except the low 7 bits of the trailing `0x80` pad byte. `UnPadBlock` only trims zero bytes, so those 7 bits never change the output.

  On the first faulted repetition the adapter also reconstructs the honest answer and exits 1 if the flip leaves the output unchanged.
- `wrong_record` replaces one server's answer with that server's honest answer to a query for a different, random index. A second client instance makes that query, so the main client's state is untouched.

- `stale_record` answers every query from a stale server (all servers for M0 and M1), built once and untimed by `buildStale` with upstream's own constructors over the database with every bit of every record flipped, in the same layout. The client's offline state still matches the current database.
  - S3: `database.Digest` over the flipped bit matrix, then `server.NewAmplify`.
  - S4: `CreateRandomEllipticWithDigest` over the flipped bits, which recomputes the row digests, then `server.NewDH`.
  - M0: `CreateRandomBytes` over the complemented bytes.
  - M1: `CreateRandomMerkle` over the complemented bytes. That builds a different tree, so the proofs fail against the client's root.
  - The judge runs S4 at 64 KiB because the S4 digest is slow.
- `drop_server` lets every server compute and time its answer, then sets one server's answer (chosen from the fault stream) to nil. That answer adds 0 to `down_bytes` and to its `down_bytes_per_server` entry. The client is not called, `correct` is null, and the repetition counts as rejected. For M0 the outcome is `aborted` and `detected` stays null.
- `bad_proof` and `re_preprocess` do not apply to these arms and exit 2, as does `switch_replica` for M0 (no verification, so nothing to reject).

If reconstruction of a faulted answer panics, the adapter records `detected=true` and logs the panic to stderr. A panic on an honest answer still exits 1.

M1 has a second guard (`refuseDecode` in `xorpir.go`). `merkle.DecodeProof` reads the hash count from the first 4 bytes of the proof, allocates a slice of that many entries, and only then reads the hashes. A corrupted answer makes the count random, so one call can reserve up to 2^32 slice headers (96 GiB). A cheating `wrong_record` run with `switch_replica --replicas-cheat` reached a 217 GB memory footprint and was killed by macOS at repetition 15. Before calling upstream, the adapter rebuilds the bytes `reconstructPIR` would pass to `DecodeProof`: the XOR of the queried row's blocks, unpadded as `UnPadBlock` does. When the count is more than a block can hold (`4 + 32·count > BlockSize`), the hash reads that follow always panic, so the outcome is the same rejection. The adapter records `detected=true`, logs "reconstruction not called" with the count, and leaves `client_recover_s` null for that answer. A smaller count allocates at most a block's worth and goes to upstream as usual. This means a malicious M1 server can make the upstream client try to allocate up to 96 GiB, which is a finding about the library and not something the adapter adds.

## Recovery

`--recovery switch_replica` (S3, S4, M1) makes up to 3 further attempts after the first rejection. Each is a fresh query for the same index from the main client, answered by honest server objects. An honest replica is a model, not a second database: upstream answers are deterministic functions of the database and the query (spec 6.1), and for M1 the same two honest servers stand in for another honest pair. With `--replicas-cheat`, each attempt draws from the fault stream and, with probability `--fault-prob`, is faulted in the same way as the first (one more `injectFault` call, so a stale replica answers from the stale server). A missing answer counts as a rejection.

`recovery_s` and `recovery_cpu_s` sum the same scheme-call timers as the first attempt (`query_gen`, every server's answer, reconstruction) over the further attempts. An M1 decode the adapter refused adds no reconstruction time. Serialisation and the fault injection itself stay outside, as everywhere else. `recovery_up_bytes` and `recovery_down_bytes` sum the encoded messages of those attempts as the client receives them, so a withheld answer adds 0. The outcome is `recovered` when an attempt is accepted with the correct record, `aborted` when 3 attempts are rejected, and `silent_wrong` when any accepted record is wrong. `abort` records `aborted` with 0 attempts. Offline records carry null for the recovery fields.

## Scheme parameters

| Arm | `scheme_params` |
|---|---|
| S3 | `tECC`, `lwe_instances` (`2t+1`), `n` (1100), `logq` (32), `p` (2), `sigma` (6.4), `bound_B`, `db_rows`, `db_cols`, `integrity_target_log2` (-64). All except `tECC` are `utils.ParamsWithDatabaseSize`, which is `utils.ParamsDefault` plus the matrix shape. |
| S4 | `curve` (P-256), `hash` (BLAKE2b-256), `element_bytes`, `db_rows`, `db_cols` |
| M0 | `servers`, `query` (`xor_shares`), `db_rows`, `db_cols`, `record_bytes`, `stored_block_bytes` |
| M1 | M0's keys plus `hash` (BLAKE3) and `proof_bytes` |

`tECC` is 4, 5, 6 and 7 at 2^23, 2^27, 2^30 and 2^33 bits (plan decision 9), computed with `scripts/integrity_amplification.py` at the 2^-64 target. Any other S3 size writes one `status="unsupported_params"` record per phase, with the reason in `error`.
